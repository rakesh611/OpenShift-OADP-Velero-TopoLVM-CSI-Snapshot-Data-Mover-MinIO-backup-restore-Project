# OpenShift SNO + OADP + Velero + TopoLVM + CSI Snapshot + Data Mover + MinIO
## Complete Practice, Backup/Restore and Troubleshooting Guide

> **Environment:** OpenShift SNO 4.18.x, OADP Operator 1.4.10, LVM Storage 4.18.4, TopoLVM, CSI snapshots, MinIO S3-compatible object storage.
>
> **Purpose:** This document records the complete lab built during the current troubleshooting/practice session and explains **what each component does, why it is used, how the components interact, how to validate them, and how to troubleshoot failures**.
>
> **Important:** Commands containing `forceWipeDevicesAndDestroyAllData: true` or equivalent destructive storage operations must only be used against a dedicated empty practice disk.

---

# 1. Architecture

The lab uses the following flow:

```text
                         OpenShift SNO
                    node: 52-54-00-2b-4e-ed
                              |
             +----------------+----------------+
             |                                 |
       Application Storage                OADP / Velero
             |                                 |
          TopoLVM                         Backup metadata
        topolvm.io                            |
             |                                 |
       lvms-vg1 SC                     +-------+-------+
             |                         |               |
         10Gi PVC                 CSI Snapshot     Data Mover
             |                         |               |
        Application                 TopoLVM          Kopia
             |                         |               |
             +------------ backup ----+---------------+
                                      |
                                  MinIO S3
                                      |
                              my-oadp-backup bucket
```

## Main components

| Component | Purpose |
|---|---|
| OpenShift SNO | Single-node OpenShift lab cluster |
| LVM Storage Operator | Creates LVM-based local persistent storage |
| TopoLVM | CSI provisioner that creates logical volumes from local storage |
| StorageClass `lvms-vg1` | Dynamic PVC provisioning through TopoLVM |
| CSI Snapshot controller | Kubernetes snapshot orchestration |
| VolumeSnapshotClass `lvms-vg1` | Tells Kubernetes which CSI driver creates snapshots |
| OADP Operator | Installs/manages Velero and OADP configuration |
| Velero | Backs up Kubernetes/OpenShift resources and coordinates volume backup |
| MinIO | Local S3-compatible backup repository |
| Node Agent | Runs on nodes and performs filesystem-level data movement |
| Kopia | Data mover repository/engine used by the node agent |
| DataUpload | Represents data uploaded during backup |
| DataDownload | Represents data downloaded during restore |

---

# 2. Why this architecture is useful

A Kubernetes backup is not simply a copy of a PVC.

There are two major categories of information:

1. **Kubernetes/OpenShift objects**
2. **Application data stored inside volumes**

Velero/OADP handles both through different mechanisms.

```text
Kubernetes objects
        |
        v
Velero
        |
        v
MinIO
```

For volume data:

```text
PVC
 |
 +--> CSI Snapshot
 |
 +--> Data Mover / Node Agent / Kopia
             |
             v
          MinIO
```

This distinction is important.

A CSI snapshot can represent a storage-level point-in-time copy, but a snapshot alone is not necessarily an independent disaster-recovery copy.

The OADP Data Mover can move snapshot data to the object-storage backup repository so that the backup is useful even when the original storage is unavailable.

## Example conceptual configuration

```yaml
apiVersion: lvm.topolvm.io/v1alpha1
kind: LVMCluster
metadata:
  name: lvmcluster
  namespace: openshift-storage
spec:
  storage:
    deviceClasses:
      - name: vg1
        default: true
        deviceSelector:
          paths:
            - /dev/sdb
          forceWipeDevicesAndDestroyAllData: false
        nodeSelector:
          nodeSelectorTerms:
            - matchExpressions:
                - key: kubernetes.io/hostname
                  operator: In
                  values:
                    - 52-54-00-2b-4e-ed
```

> The exact `nodeSelector` structure can vary by installed LVM Storage API version. Always use `oc explain lvmcluster.spec.storage.deviceClasses.nodeSelector` for the exact cluster schema before applying a custom manifest.

If the device is definitely disposable, force wiping may be enabled:

```yaml
forceWipeDevicesAndDestroyAllData: true
```

**Do not use this on an OS disk or a disk containing valuable data.**

# 16. What the CSI snapshot actually means

A CSI snapshot is a storage-level point-in-time representation.

It is useful for:

- fast local recovery
- cloning/restoring volumes
- integration with backup software

But:

```text
CSI snapshot != complete disaster recovery backup
```

If the storage device itself is destroyed, a local snapshot may also be lost.

Therefore OADP Data Mover can copy snapshot data into object storage.

# 19. Does every application namespace need another OADP?

**No.**

This is an important concept.

Normally you install one OADP instance in:

```text
openshift-adp
```

and it can back up multiple namespaces.

For example:

```text
default
app1
app2
database
frontend
backend
```

One Velero/OADP installation can select:

```yaml
includedNamespaces:
  - app1
  - app2
  - database
```

or all namespaces, depending on the backup design.

Therefore:

```text
1 OADP deployment
       |
       +---- namespace A
       +---- namespace B
       +---- namespace C
       +---- namespace D
```

You do **not** normally deploy one OADP operator per application namespace.

The first backup used:


but:

```yaml

```

This means Velero created/used CSI snapshots, but the snapshot contents were not necessarily moved into the object-storage repository.

This is a critical distinction.

```text

Create CSI snapshot

       |
```

# 32. Enable Data Mover

For OADP 1.4.x, enable the node agent and Kopia-based data movement.

Example DPA configuration:

```yaml
configuration:
  nodeAgent:
    enable: true
    uploaderType: kopia

  velero:
    defaultPlugins:
      - aws
      - openshift
      - csi
    defaultSnapshotMoveData: true
```

The important fields are:

```text
nodeAgent.enable: true
uploaderType: kopia
defaultSnapshotMoveData: true
```

## Why?

`defaultSnapshotMoveData: true` tells Velero/OADP to move snapshot data to the backup repository.

The Node Agent performs the actual data transfer.

Kopia provides the repository/data-management layer.

## Object storage

Prefer:

- external S3
- enterprise MinIO cluster
- Red Hat-supported object storage

- separate failure domain

Do not use:

Actual values must be based on business requirements.

# 70. Snapshot versus Data Mover

## CSI snapshot

Advantages:

- fast
- storage-native
- point-in-time
- useful for local restore

Limitations:

- depends on underlying storage
- not automatically an off-cluster backup
- storage failure can destroy both source and snapshot

## Data Mover

Advantages:

- copies volume data to object storage
- better disaster recovery
- can restore when original storage is unavailable
- integrates with Kopia repository

Trade-off:

- consumes object-storage capacity
- consumes network bandwidth
- consumes CPU/storage I/O
- backup takes longer than metadata-only operations

---

# 71. Why both snapshot and Data Mover are used

The desired architecture is:

```text
             PVC
              |
              v
        CSI Snapshot
          /       \
         /         \
        v           v
Fast local       Data Mover
restore              |
                     v
                   Kopia
                     |
                     v
                   MinIO
```

This gives two recovery mechanisms:

### Local recovery

Use the CSI snapshot when the source storage remains available.

### Disaster recovery

Use the object-storage copy when the source storage or original cluster is unavailable.
